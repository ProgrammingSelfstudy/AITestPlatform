## 权限模型：不做登录页（必须遵守）

没有登录页或用户身份鉴权。没有共享口令只能查看；创建任务、取消执行和提交审核都需要同一个写入口令，不授予账号或节点权限：

1. 服务端默认只监听 `127.0.0.1`；局域网访问必须显式开启 `PLATFORM_ALLOW_LAN=1`，只能在可信内网使用。
2. `/api/nodes` 等接口暴露的是节点和设备清单（设备序列号、型号），不含账号凭证。
3. 审核记录、审核统计、脱敏训练样本和回放与其他只读页面一样在局域网可访问，不需要口令。**不开放账号信息接口**；账号凭证仍然只走「节点令牌 + 一次性」的接口，不经过前端。
4. 节点令牌（`NODE_TOKEN`）是节点接入的唯一凭证，必须显式配置，代码里不写默认值，不写日志。
5. 所有浏览器 POST 仍经过现有 Host / Origin / `X-Requested-With: ai-test-platform` / `Content-Type: application/json` 校验；开发代理保留浏览器 Host。创建、取消和审核提交在这之后还必须通过 `x-review-token` 校验。节点协议与本机 `server create-task` 不受影响。

## 其他取舍

- 模型来源只做本机会员（`claude` 命令行、`codex exec`），**不做 API Key 路径**，只留接口位；规划里 LiteLLM、mitmproxy 已换成 Rust 自研方案。
- 节点上报的 `vision` 来自技术验证里的实测，不是探测结果；是否已登录会员、额度够不够，要在 P0 后半段单独验证。
- 审核数据用于训练模型的路径尚未定（见 PoC 仓库规划九.8），先保证审核记录可导出成训练样本。

## P0 验证结论（2026-11-21）

| 验证项 | 结论 | 依据 |
|---|---|---|
| Rust 经 `claude` 命令行调 Claude 会员 | **可行** | `crates/agent` 的运行器对真实命令行跑通：非交互、流式输出（`stream-json`）、提示词走 stdin、剔除 `ANTHROPIC_*` / `OPENAI_*` 环境变量后仍走会员登录 |
| `rmcp` 起设备 MCP 服务 | **可行** | `rmcp 3.11.0`；真机上 `observe` 返回控件树文字 + 合法 PNG 截图；找不到元素明确报错、不乱点；没有 `HAFA_SERIAL` 拒绝启动 |
| 整条链路（claude 会员 → Rust MCP → 真机） | **可行** | 真实调用：模型只调用了 `observe`，读到锁屏页并如实说明截图全黑 |

**运行器已具备的能力**：卡住检测（超时没有任何输出就整组杀进程）、总时限、额度识别（命令行报错文案 + `rate_limit_event` 状态）、登录失效识别、异常退出带出原始 stderr、记录模型发起的工具调用、`--allowed-tools` 白名单。

**踩过的坑，别再踩**
- 杀进程要**杀整个进程组**：只杀 `claude` 本体，它拉起的 MCP 服务等子进程会残留并抓着管道，运行器会被拖住几十秒。
- 额度文案要允许 `your` 和 `limit` 之间夹一个词（weekly / daily），否则「reached your weekly limit」识别不出来。
- 节点与设备要在**事务**里一起写、一起读（快照），否则会出现「节点离线设备还空闲」「节点在线但没有设备」。
- 测试里不要执行新建的可执行文件（macOS 首次执行会被系统扫描，偶尔慢好几秒），用 `/bin/sh` 去读脚本。
- 读退出码不要经过管道（`cmd | tail` 拿到的是 `tail` 的）。
- sqlx 0.9 要求拼接出来的 SQL 显式标注 `AssertSqlSafe`；来自数据库的标识符先校验字符集再拼。

**Claude 会员额度（技术验证里一直没量化的数据）**：7 天窗口已用 **84%**（告警线 75%），2026-11-22 03:00（UTC+8）重置；5 小时窗口约 15%，没有开通超额。一次几百 token 的小调用约占 1 个百分点。开发期间真实调用要克制，测试优先用假的 `claude` 脚本。

**环境**：本机直连 npm / crates.io / Homebrew 的 ghcr 经常断流，已在项目内改用镜像（`.cargo/config.toml`、`web/.npmrc`，只影响本仓库，删掉两个文件即撤回）；PostgreSQL 17 用 Postgres.app（`~/Applications/Postgres.app`，数据在 `~/.local/var/postgresql@17`），开发库只监听本机。

**留给 P1 的已知事项**
- 设备 MCP 服务现在**没有护栏**（卡住检测、步数上限、高危页面返回 `need_human`、轨迹记录），所以只能用来验证链路，**不能当执行层用**。
- 锁屏时截图是黑的：执行前必须先唤醒并解锁（技术验证里 `setup_env` 的 `ensure_awake`）。
- 模型 / 角色配置、`codex exec` 运行器、看门狗对 GPT 链路的处理还没做。
- 登录鉴权仍未做（见上文约束）。

**`automation/hafa_automation`（Python，来自技术验证）**
- 改动只有三类：配置改读环境变量；账号改从 **stdin** 收（不读文件、不进命令行、不进环境变量、不打印）；输出改成 JSON 行事件。
- 契约：退出码 0 成功 / 1 某步失败（事件带当前页面文字）/ 2 用法错误 / 3 需要人工（屏幕解不开）/ 4 需要凭证。
- 账号标识用租约 id（不透明），脚本只用它判断手机上是不是已登录这个账号，不再用序号。

**`node::setup_runner`（Rust）**
- 凭证只经 stdin；转发任何输出前**在 Rust 侧再脱敏一次**（不把「脚本不会泄露」当前提）；环境变量清空后只放行基础变量和 `HAFA_*`；超时整组杀进程；`AccountArg` 的 `Debug` 不打印账号密码。
- 事件实时转发；退出码映射成 `Ok / StepFailed / NeedHuman / NeedCredentials / Usage / Crashed / Timeout`；退出码 0 但没有 `done` 事件、或既有 `error` 又退出 0，都不当成功。17 个测试。

### 已完成：用例导入与库表（`crates/server/src/cases.rs`、迁移 `0002`）

- **库表**：`projects`、`test_cases`（字段见 `docs/数据模型.md`，另加了 `platforms`、`refs`、`note`、`blocked_reason`）。库里有 check：`steps`、`expected` 不能为空数组。
- **导入是本机命令行，不是 HTTP 接口**：`server import-cases --dir <目录> [--project hafa] [--block 编号=原因]`。目前没有鉴权，一个能读服务器文件系统的接口等于任意文件读取；测试里专门验证了「不存在导入接口」。
- **强制的规则**（都有测试）：
  - 用例数据里账号相关的键（password / username / account / email / token / secret 等）必须是 `{{account.xxx}}` 占位符，写明文就拒绝导入，**错误信息里不回显值**（它很可能就是明文密码）；
  - **全有或全无**：任何文件有问题，一个都不导入，并且把**所有**问题一次报出来；库写入也在一个事务里，中途失败整体回滚（连项目一起）；
  - **幂等**：重复导入不改版本，只有内容真的变了才 `version + 1`（run 要靠版本号复现当时的用例）；只有状态变化（如解除受阻）不加版本；
  - **负例由 `level = 故意失败` 推出**，不靠编号后缀（TC-09 没有 `-F` 后缀也是负例）。
- **只读接口**：`GET /api/projects`、`/api/projects/{project}/cases`（按自然顺序，TC-10 在 TC-02 后面）、`/api/projects/{project}/cases/{code}`（带下发给节点的 `spec`）。
- **已用真实数据导入开发库**：PoC 的 16 个用例，5 条负例恰好是 PoC 里那 5 条，TC-07 标为受阻（房主不能下麦），库里没有明文账号字段；第二遍导入全部「无变化」。
- **做过变异检查**：把「内容变了才加版本」的比较条件改成永远为真，3 个测试失败；已还原。
- 导入**不能**用 `AppState::init`（它会把所有节点置离线），所以抽出了只跑迁移的 `server::migrate`。

**踩坑**：YAML 里没有「受阻」信息（PoC 是在批跑脚本里排除了 TC-07），所以导入时要用 `--block` 显式指定。

- **设备占用锁**：部分唯一索引 `runs_device_lock`，同一台设备同一时刻只有一个活跃 run。`node_lost`（节点掉线宽限期内）也占着设备，否则节点重连前别的排队任务会把手机领走，想续跑时设备已被占。
- **Judge 没跑成时最终结果只能是「待确认」**：check 约束，不能用执行员的自评顶替。
- **blocked 必须有原因**：统计完成率要区分链路 / 环境故障。
- `finished` 的最终结果不能是 blocked。

**应用层的规则**
- **run 创建时就绑定到一个节点**，只有这个节点的连接能领走、推进它：「谁发起谁付额度、不能委派」是靠**结构**保证的（不存在跨节点调度这个动作），不靠校验发起人，因为现在没有登录。创建任务时还校验所选节点真的有所选的模型来源。节点操作别的节点的 run，一律拒绝，且一次都不生效。
- **用例内容快照进 run**：排队期间用例被改了，这次执行仍用创建时的内容，能复现。
- **最终结果由服务端按逐条判定重新算，不信节点报的**：有 failed 就是 failed；没有 failed 但有 uncertain、判定条数和预期条数对不上、或有重复 / 越界的编号，就是 uncertain；只有全部 passed 且恰好覆盖每一条预期才是 passed。**漏判的预期不能被当成通过。**
- **节点掉线**：执行 / 判定中的 run 转 `node_lost`，**不直接判失败**；还没开始的退回排队。**节点重连**时服务端对它声称仍在跑的 run 按宽限期决定继续还是放弃（已有执行员结果的回到判定阶段）；服务端以为在跑、节点却没有的（节点重启丢了本地进度）判受阻，并释放设备。
- 节点心跳里的设备状态**不能覆盖**有活跃 run 的设备（服务端说了算：busy）。
- 领取用 `FOR UPDATE SKIP LOCKED`，10 个并发领取 5 个 run、3 台设备，恰好领走 3 个，没有重复。
- 非法状态流转明确报错，不静默忽略。

**测试**：状态机纯逻辑 8、数据库 28、WebSocket 联动 6。**做过变异检查**：去掉设备 busy 保护 → 2 个测试失败；重连时不管宽限期 → 1 个失败；已还原。

**踩坑（真实 bug，测试抓到的）**：同一任务的多个 run 在同一个事务里创建，`queued_at`（事务开始时间）完全相同，排序退化成按随机 UUID，**任务内的执行顺序是乱的**。改用单调递增的 `seq` 列排队，并加了「20 个 run 严格按创建顺序领取」的回归测试。

**还没做**：把状态机接到 WebSocket 派发（服务端主动给节点发 `run_assign`、收 `step` / `executor_done` / `judge_done` 等并落库）、宽限期过期的定时清理（`expire_node_lost` 已实现，还没有定时调用它）、取消时通知节点、创建任务的入口（目前只有库函数，没有 HTTP 接口，也没有命令行）。

### 证据文件地址签名、判定前登录检查、前端改版（2026-11-21）

### P3 第一步：脚本归档层（2026-11-21）

分期建议里 P3 的前提是「候选合规才入库，自检通过才归档，按用例版本记录来源执行、脚本版本和内容摘要」。生成核心此前只到内存产物为止，没有任何存储。这一步补上存储、版本和状态流转，**不含**自检执行、平台入口和零模型回归，那些还没做。

**库表 `scripts`**（迁移 `0012`）。字段：用例、版本（用例内从 1 递增）、依据的用例版本、来源执行、文件表（路径到源码）、内容摘要、生成时的模型来源／名称／强度、状态与状态说明。库层约束兜底：状态取值、摘要为 64 位十六进制、文件表必须是非空对象、模型来源只能是 `claude_cli` 或 `codex_exec`、同用例同版本唯一、同用例同内容唯一。绕过模块直接写库写不进这些脏数据，有测试覆盖。

**归档模块 `crates/server/src/scripts.rs`**。服务端不依赖 `agent`，所以不重复做静态校验，也不声称校验过脚本内容里有没有凭证，那由生成端的 `scriptcheck` 负责。入库前服务端再做一遍不依赖模型的硬检查，任何一条不满足都拒绝，且不留记录：

- 来源执行必须属于这个用例，用例版本和当前一致（用例改版后，旧版本的执行不能生成新脚本），Judge 已完成，最终结果为通过，且每条预期都有通过的判定项。待人工确认、失败、受阻都不能生成脚本。
- 文件名白名单与 `scriptcheck` 规则 0 一致：必须有 `test_<编号>.py`，可选 `pages/<编号>_pages.py`，别的一律不收；最多 6 个文件，单个不超过 64 KiB，不能为空，不含 NUL。
- 生成端给的单文件摘要，服务端按原始 UTF-8 内容重算比对，少一个或错一个都拒绝，并指出是哪个文件。
- 整套内容摘要 = 按路径排序，把「路径、NUL、单文件摘要、换行」逐个连起来取 SHA-256。同用例同样内容只归档一次，重复提交返回已有版本。
- 先锁住用例行再分配版本号，并发归档同一用例不会重复或跳号（6 路并发有测试）。

**状态只能顺着走**：候选 → 自检通过 → 获准 → 下线。候选和自检通过都可以被拒绝，获准后只能下线，拒绝和下线是终点；**不允许跳过自检直接获准**，也不允许回退。失败的迁移不改状态。

**验收**。全工作区 35 个套件、523 个用例通过，0 失败，无新增警告；新增 5 个单元测试（文件名、摘要、状态机）和 13 个数据库测试。

**没做、需要注意**
- 这一步没有 HTTP 接口（第二步已补，见下节）、没有页面，也没有自检执行：「自检通过」目前只是一个状态值，**还没有任何代码会真的去跑自检并改状态**。
- 生成核心还没有接到归档上：`scriptgen_dev` 仍然只输出到标准输出，没有人把它的产物写进 `scripts`。
- TC-04 候选脚本的断言缺口（见上一节）仍然没有补，所以它不能走到获准。
- 常驻的开发库要等服务端下次启动时才会执行迁移 `0012`，目前没有接口用到这张表，所以没有影响。

**发现并修复两个缺陷**：

1. **带账号租约的真机执行必然失败（审计消耗了一次性脱敏清单）。** 执行员启动前有一步「审计」，它用和真实会话同一套 MCP 配置启动一次设备服务来读工具清单；设备服务读完脱敏清单文件就立即删除（这是有意设计，明文不能留盘）。审计在前，把文件消耗掉，真实会话再启动设备服务时读不到清单，在回复 initialize 之前就退出。已手动复现：连续两次用同一路径启动，第二次报 `读取脱敏清单失败：No such file or directory`。此前没有发现，是因为所有测试都用假设备。修法：新增 `build_audit_args`，审计参数与真实运行一致，**只是不带脱敏清单**（审计只列工具、不执行动作）；真实会话仍完整带上，没有放宽「读完即删」。环境变量名抽成共用常量 `SECRETS_ENV`，避免节点和 agent 两处字符串漂移。

## P3 · 按自检失败修正，版本 3 自检通过

## P3 · 获准、下线与「回归脚本」页面

**服务端**（人的决定，用审核口令，和创建任务、提交审核同一套；节点令牌不能替人决定）：
- `POST /api/scripts/{id}/approve | retire | reject`，请求体 `{note}`。获准的原因可不写，下线和拒绝必须写（最多 300 字）。
- 状态机在 `scripts::transition`：不能跳过自检直接获准；**同一用例同时只能有一个获准版本**（先下线旧的才能获准新的，并发时由迁移 `0013` 的部分唯一索引兜底）；**用例内容变过的旧脚本不能获准**（脚本依据的用例版本必须等于用例现在的版本）；获准后只能下线，拒绝和下线是终点，不能恢复。获准前锁住用例行，两个脚本同时获准会串行化。
- 人的决定追加在状态说明后面，不覆盖自检输出；总长不超过库里的 2000 字上限，放不下时截掉旧输出的开头、保留末尾和完整原因。
- `GET /api/projects/{project}/scripts`：项目里所有脚本版本，带用例编号和标题，不含源码。

**顺手修了一个会在真实输出变长时才出现的缺陷**：库里 `status_note` 限 2000 字，而自检回报最多允许 3500/4000 字，输出一长就会在写库时失败。之前的测试用的都是短输出，没发现。现在节点只留 1500 字末尾，服务端对自检输出的上限收紧到 1800 字，超出直接 422，而不是写库时才报错。

**前端**：新增「回归脚本」页（`#/scripts`）：按用例、版本列出全部脚本；状态用标签区分（候选待自检、自检通过待获准、已获准、已拒绝、已下线）；展开能看文件、依据的用例版本、生成备注和状态说明；按状态只显示可用的按钮（候选只能拒绝，自检通过可获准或拒绝，已获准可下线），点开填原因，再输入审核口令。按钮只决定显示，真正的规则在服务端。「已获准」用绿色标签，页面说明里写明它只表示可被平台选来回归，不是测试通过。

**验证**：服务端 12 个新增用例（完整流程、不能跳过自检、一用例一个获准、用例变过不能获准、拒绝和下线要原因、令牌与节点令牌、长输出不超限、按项目列出）加状态说明截断的单元测试；变异检查：去掉「用例版本没变」和「另一个获准版本」两道检查，对应两个用例失败。全量 565 个通过。页面在浏览器里用真实数据看过：三个版本、展开详情、获准对话框都正常；**没有在真实库里点确认**，版本 3 仍是「自检通过」，获准是你的决定。

**仍然没做**：平台按版本回归（选已获准的版本，在节点上跑）；前端没有自动化测试（项目里本来就没有前端测试脚本，页面只做了类型检查、构建和浏览器里的手工检查）；自检不领账号租约；预期 3 的勾选仍是间接推断。

## P3 · 按版本回归，以及 accounts 测试的真实根因

**回归**（`node regress <用例编号> [--project hafa] [--serial …]`，不花模型额度，会占用手机）：
- 取该用例当前**已获准**的脚本版本（`GET /api/projects/{project}/cases/{code}/approved-script`，没有获准版本就 404，节点在占用手机之前就报错），在本节点真机上用 pytest 跑，结果记到新表 `script_regressions`（迁移 `0014`），页面「回归脚本」新增「最近回归」列，展开能看原始输出。
- **失败是回归的结论**：如实记下通过或失败和原始输出，**不改脚本状态**，也不自动下线。失败可能是产品退化，也可能是脚本随界面改版失效，需要人判断。
- **环境问题不记**：设备掉线、前置状态或关房失败、超时只报错。把手机掉线记成「回归失败」会让人误以为产品退化。
- **获准的脚本是项目资产**：不要求脚本来自本节点，任何认证节点都可以在自己的设备上回归，结果记在回报的节点名下。只有已获准的版本能记（候选、自检通过、已拒绝、已下线都返回 409）。
- 自检和回归共用同一套「写成 generated 包、跑 pytest、识别环境问题」，只是后续处理不同：自检的失败会拒绝候选，回归的失败只是记录。
- 测试：服务端 3 个 HTTP 用例（取已获准版本、只能记在已获准版本上且页面带最近一次、格式与认证），节点端 6 个端到端用例（通过、失败是结论、环境问题和超时不记、没有获准版本不占手机、下线后用新版本、别的节点也能回归）；变异检查：让回归把任何结果都当通过，失败用例报错。

**这次没有做的：在平台页面上点按钮发起回归。** 现在回归由节点命令行触发，结果上报到平台并显示；页面发起要走任务派发那一整套（派发给节点、节点领取、取消、状态），是另一个独立的功能，没有在这一步里做。

**真实根因：`server/tests/accounts.rs` 的 `导入设备字段覆盖命令行_重导更新绑定且只输出数量`。** 前面我把它记成「偶发失败，没查根因」，这是不对的：迁移加到 14 个之后它在全量并行下稳定复现（连续 3 次）。先把子进程的 stdout 带进断言消息，看到的是：多个测试并行迁移同一个库，抢 `pg_advisory_lock` 等了 1.46 秒，超过 sqlx 的慢语句阈值（1 秒），sqlx 打了一条警告；而服务端把**日志写在 stdout 上**，混进了 `import-accounts` 本该只输出的「已导入 2 个账号」。两处修复：服务端日志改写 stderr（stdout 留给命令输出，对所有子命令都成立，这是设计上的修正，不只是为了测试）；测试的日志级别改成 `warn,sqlx::query=error`，排除与被测行为无关的慢查询警告，其他警告仍保留，所以「不泄露账号」的检查没有被放宽。修复后连续 3 次全量并行 574 个全部通过。

**另一个偶发仍未查**：`agent/tests/codex_run.rs` 里 `need_human期间不算卡住` 这次全量里又失败过一次，单独跑通过，是靠时间窗口判断的测试，机器上同时跑着服务端、节点、前端和数据库时容易触发；没有改。

## P3 · 页面发起回归（2026-11-22）

「回归脚本」页里，已获准的版本现在有「回归」按钮；之前只能在节点上敲 `node regress`。

**流程**：页面选自己的节点、填个人令牌、审核口令 → `POST /api/scripts/{id}/regress` 排一个请求（表 `regression_requests`，迁移 `0015`）→ 节点每 5 秒来领（`PUT /api/node/regression-requests/claim`，带上它要用的那台设备）→ 在自己的手机上跑，结果照旧记到 `script_regressions` → 节点回报请求结果（`PUT /api/regression-requests/{id}/result`）。页面「最近回归」列显示排队、运行中、没得到结论（带原因）或回归结果；排队中的可以取消，被节点领走的不能。

**规则**：
- **只能发到自己的节点**（规则 9）：个人令牌对应的用户必须是节点属主；写接口和创建任务同样要审核口令。
- **只有已获准的版本**：排队时检查一次，节点领取时再检查一次（排队期间被下线就标失败，不跑）。节点执行前还确认「获准版本仍是请求的那个」，换了版本就不回归，免得把别的版本的结果记成这次。
- **手机互斥靠设备行锁**：领取回归和派发 run 都先锁设备行；派发另外排除有「运行中」回归的设备，节点心跳报「空闲」也盖不掉这把锁。反过来，手机上有任务在跑，回归继续排队。
- **失败是结论**：回归失败时请求仍是「已完成」（得到了结论）；环境问题、版本换了这类没得到结论的才是「没得到结论」，原因原样写下，不记成回归失败。
- **不会永远占着手机**：节点进程启动时作废自己之前没回报的请求；服务重启时全部作废；领走后 30 分钟没回报，下次领取时作废。节点短暂断线不算，因为手机上可能仍在跑。
- 同一脚本在同一节点上同时只有一个未结束的请求（部分唯一索引），连点两次只排一份。

**节点**：配了 `HAFA_DEVICE_ALLOW` 且恰好一台设备时才接页面请求（多台设备要显式指定，仍用 `node regress --serial`）。`node_id` 要等节点第一次连上服务端才有，所以配置拿不到时每 5 秒重试。

**验证**：节点端到端 10 个新用例（排队、领取、跑完、回报；失败是结论而环境问题没有结论；别人的节点、没令牌、没口令、候选版本、重复排队都被拒且不留记录；回归占手机时不派任务、任务占手机时不领回归；排队期间被下线；换版本不回归；取消；节点重启与超时释放设备；别的节点领不走也不能代报）；变异检查：去掉派发里排除回归占用设备的那一行，互斥用例失败。前端类型检查和构建通过。

**没有做**：页面没有在真实库和真机上点过「回归」（需要你自己的个人令牌和审核口令，也会占用手机）；前端仍没有自动化测试。

**`agent/tests/codex_run.rs` 的偶发失败**：把 `need_human期间不算卡住` 的等待加到 4 秒（要明显超过 2.5 秒的卡住阈值，之前 1.6 秒在高负载下余量太小）。但全量并行跑时，其他靠 2.5 秒阈值判断卡住的用例（`动过手机后卡住`、`工具调用挂住`、`同一个目录不能重复执行`）在机器负载高时仍会偶发多判一次卡住，每次失败的用例不同，单独或只跑这个文件连续 6 次都通过。根因是续跑进程在高负载下启动超过阈值，不是某个具体缺陷，没有再改阈值。

## P3 · 自愈分诊（2026-11-22）

获准脚本回归失败后，在来源节点上分诊：**只有确定是控件定位失效才产出修复候选**，其余不动脚本。节点命令 `node heal <脚本编号> [--serial …] [--app-info …]`，页面「回归脚本」显示结论。

**流程**：
1. 平台给材料（`GET /api/scripts/{id}/heal-source`）：脚本源码、最近一次回归。先挡掉不该花额度的情况：不是已获准、没回归过、最近一次回归通过、这次失败已分诊过。
2. 节点在手机上把脚本**重跑一遍**取新证据（失败那一刻的控件文字，插件写的 `*-elements.txt`）。重跑通过 → 原失败可能是偶发，记「分不清」，**不调用模型**；设备掉线、前置失败等环境问题 → 只报错，不记分诊。
3. 用来源任务里 Judge 的角色配置和本机会员命令行调 `agent::scriptgen::heal`：输入是原用例、原轨迹、Judge 证据、当前脚本、失败输出、控件文字。模型只能给三种结论：`locator_broken` 定位失效、`business_bug` 业务行为错误、`unsure` 分不清（拿不准就选它）。
4. 回报 `PUT /api/scripts/{id}/triage`。

**不信任模型的几道硬检查**（`agent::scriptgen::heal` 和服务端各守一层）：
- 「定位失效」必须带两个完整文件，且过和生成同一套静态校验；**断言数量不能比原脚本少、内容不能和原脚本相同**（`assert_count` 数语句级 `assert`，是启发式，不是断言语义检查）。不过关先让模型改一轮，仍不过就降为「分不清」，不采用。
- 业务行为错误、分不清即使模型带了文件也丢弃。结论不在三种之内、输出无法解析、原因含敏感值，一律降为分不清。
- 额度用完直接停，**不降级、不记分诊**，恢复后同一次失败还能再来；不使用 API Key。
- 服务端：只有已获准的脚本、只针对**最近一次失败的回归**、同一次失败只分诊一次（`script_triages.regression_id` 唯一）；只有定位失效能带修复文件。修复候选和分诊记录在**同一个事务**里写，修复被归档检查拒绝（内容与已有版本相同、摘要对不上等）时分诊也不留下。

**修复只是候选**：新版本记下 `healed_from`（修自哪个版本），状态是候选，要重新自检、人工获准；**原获准版本在人决定前不动**，不会被替换。页面上修复版显示「修自 vN」，回归失败旁显示分诊标签，展开能看依据。业务行为错误显示「疑似产品缺陷，待人处理」：平台目前**没有缺陷系统**，这里只是标出来，不会往任何外部系统建单。

**验证**：
- 模型端 11 个用例（假 Claude）：定位失效产出带哈希的修复；业务错误丢弃文件；分不清；原样不改或删断言都降级；违规一轮后改正；无法解析、结论不认识；额度用完；凭证不进入输入、原因含敏感值不采用；来源执行不是整体通过不调模型；变异检查：去掉「断言不能少」，删断言用例失败。
- 节点端到端 10 个用例：定位失效产出候选且原版本仍获准、记下来源；业务错误不增脚本、失败回归保留；重跑通过不调模型；重跑环境问题不分诊；额度用完不记分诊；不该分诊的情况（候选、没回归、回归通过、不存在）都不调模型；同一次失败只分诊一次、再回归失败后才能再来；不是本节点的脚本不能自愈；服务端拒绝不合规分诊且什么都不留下。变异检查：去掉「只有已获准才能分诊」，对应用例失败。

**没有做 / 已知限制**：

- 修复候选的自检、获准仍走原来的命令和页面，没有一键串起来。

| 能不能审计它调用了什么 | 能。`stream-json` 输出里每次工具调用有 `step_update` 事件，带 `tool_name` 和 `ServerName/ToolName`；`init` 事件列出它有 60 个内置工具 |

### 运行器（`agent::agy_cli`）
- **每次调用一个临时目录**：独立 `HOME`（含这次专用的 MCP 配置，链接登录态）、**空的工作目录**、会话级设置文件（只放行白名单里的 MCP 工具）、日志文件。用完整个删除，符号链接只删链接，不动真实的登录态。
- **审计白名单**：流式事件里凡是白名单之外的工具调用（包括默认放行的内置工具）都记为 `violations`；被自动拒绝的动作记为 `denied`。`Outcome::ok()` 要求没有失败、没有违规、没有被拒动作：评审员只有这种情况下才能采信结果。
- **规则 1**：剔除 `GEMINI_*`、`GOOGLE_*`、`AGY_*` 环境变量；`check_login` 跑 `agy models --log-file`（不调模型、不花额度），只接受认证方式 `consumer`，API Key、应用默认凭据、企业网关、读不出来都拒绝；错误说明里不带日志里的账号信息。
- **额度**：识别出额度用完返回 `Failure::Quota`，不重试、不换计费方式。
- **超时**：只有总时限（流式输出里没有可靠的「还活着」信号）；超时杀整个进程组，`agy` 起的 MCP 子进程一起杀。
- **输出上限** 16MB，防止吃光内存。

### 验证
- 12 个假脚本测试：提示词不进参数、独立 HOME 和空工作目录、链接而不是复制、环境变量剔除、用完清理且不动真实登录态、白名单审计（读文件、别的 MCP 服务、没放行的工具、ACTIVE 和 DONE 只算一次）、被拒动作、失败分类（登录、额度、其他、状态非 SUCCESS 不当成功）、没有结果事件、超时杀进程组含子进程、起不了进程、并发隔离、登录检查。变异检查：不剔除环境变量、审计不记违规、不清理临时目录、超时不杀进程组，对应测试都失败。
- **对真实 agy 的集成测试**（`tests/agy_real.rs`，默认忽略，`-- --ignored` 手动跑）：登录检查通过，经证据 MCP 取图和步骤文字，审计干净，`served.json` 和引用一致。约 47 秒，用了约 1.6 万 token。**agy 升级后先跑它。**

### 限制

- **还没接进 Judge**：这一步只是运行器本身。接入还要：把证据 MCP 的运行目录加锁、清理 `served.json` 这套逻辑从 `judge.rs` 里抽出来共用；`CLAUDE.md` 里的规则还没改（规则里只有 `claude` 和 `codex exec` 两条路径）。

## agy 接进 Judge（2026-11-22）

`agent::judge::run_judge_agy`：agy（Gemini）作为评审员，和 Claude 评审员用**同一套提示词、同一份证据服务、同一份核对逻辑**。

**重构**：`judge.rs` 里抽出三块共用代码，核对证据只有一份实现，不因评审员不同而放宽：

**agy 路径的几条规矩**：
- 判定规则合并进用户消息（agy 没有系统提示词开关）。

- 调用前用 `agy models` 确认是个人账号登录；额度用完标记 `quota_exhausted`，不重试、不换计费方式。

**真实运行里发现的问题（也是审计起作用的例子）**：第一次用真实 agy 走完整 Judge 路径时，它**两次尝试 `read_file`**（被默认拒绝），审计把它标成越界，整次评审转待人工确认，没有被放过。原因是 Judge 提示词写的是「用 evidence 的 image 工具取图」，Claude 命令行把证据工具直接列成 `image` / `step_text`，一句话够了；agy 自带读文件、命令行、浏览器等内置工具，MCP 要经通用的 `call_mcp_tool` 调，不说清楚它就去读文件。给 agy 的提示词前面加一段专门的工具使用说明（`AGY_TOOL_GUIDE`：用 `call_mcp_tool`，ServerName 填 evidence，ToolName 填 image 或 step_text；不要用其他任何工具，否则评审作废）后，真实运行连续 3 次都没有再越界，结论通过，引用和 `served.json` 一致。

**限制**：

## 节点生成用例（第 3 步）

- **流程**：页面创建任务 → 服务端排一个 `casegen_request` → 节点每 5 秒轮询领取（只领本节点的，规则 9）→ 用本机「测试用例」角色的模型根据文档和截图生成 → 回报原始输出 → **服务端是格式的唯一裁判**，用 `cases::parse_case` 同一套规则逐条校验，任何一条不合格**整批拒收、一条都不入库**，请求转失败并说明原因。
- **入库规则**：用例编号由平台分配（`GEN-<请求前 6 位>-<序号>`，不信模型给的，避免覆盖已有用例）；不能是「故意失败」级别；`data` 和文字里的明文密码都拒（错误里不回显值）；最多 40 条。入库状态是 `draft`，`create_task` 现在会拒绝非 `approved` 的用例（说明「还没有通过复核和人工确认」），老用例默认 `approved` 不受影响。
- **模型怎么看图**：Claude 用纯文本角色隔离（无内置工具、无 MCP），截图经 `--input-format stream-json` 的图片块传入；Codex 用只读沙箱 + `-i` 传截图（`-i` 是多值选项，后面要加 `--` 再给提示词标记 `-`）。UI 设计链接只作为文字写进提示词，模型没有任何工具能打开它，提示词里也要求「不要假装看过链接」。文档、链接、截图都在提示词里声明为数据而不是指令。
- **角色选择**：请求没指定就用节点第一个「测试用例」角色，指定了不存在的不退回别的；节点上报过角色时，服务端创建请求前就校验有检测通过的测试用例角色（没有就提示去配置），旧版节点不拦、节点领取时如实报没有角色。额度用完立即回报失败，不换计费方式。
- **超时**：领走超过 30 分钟没回报的请求，下次有节点领取时转失败，不会一直占着「同模块只能一个」。
- **测试**：服务端接口集成测试（领取、别的节点领不到、不能代报、格式不合格整批不入库、失败后可重提、草稿不能执行）、5 个节点端到端测试（假生成函数：成功入草稿、没角色、指定角色不存在、额度用完、服务端整批拒收）、agent 单元测试。真实调用（`cargo test -p agent --test casegen_real -- --ignored`，只用合成文档和一张合成截图）：Claude 15 秒、Codex 51 秒，都生成了合理的用例（占位符写法正确）。
- **还没做**：评审员复核和人工确认（计划第 4 步）、前端必填表单和模块页（第 5 步）。agy 的图片输入没验证，所以 agy 不能当测试用例角色。生成用例的质量只用合成文档看过，没有用真实项目评估。

## 评审员复核和人工确认（第 4 步）

- **流程**：生成成功、用例以草稿入库后，节点马上用本机「判定员」角色当评审员复核（请求指定了就用它，没有就用第一个，不退回别的）→ 回报意见 → 服务端更新状态。评审员**只看文档和用例文字，没有任何工具**（Claude 走纯文本角色隔离；agy 不挂 MCP，调用了任何工具整次作废）；文档和用例在提示词里声明为数据，要求「拿不准一律交给人」。
- **状态**：`draft`（刚生成）→ `reviewed_ok`（评审员认为文档里有依据、预期可判定）/ `needs_human`（有疑问或没跑成）→ 人确认后 `approved`（才能执行）或 `rejected`。**评审员的通过只是意见，不会让用例能执行**（规则 5：不强行通过）；`create_task` 只认 `approved`。
- **评审员没跑成一律转待人工确认**：没有判定员角色、额度用完、输出不是合法 JSON、没给出某条的结论、结论不认识，都是 `needs_human`，原因写进备注，不当通过。只更新这次请求生成的、仍是草稿的用例，重复回报不会改已复核的。
- **人的决定**：`POST /api/modules/{id}/cases/{code}/decision`（批准或拒绝）、`POST /api/modules/{id}/approve-reviewed`（一键批准评审员认为没问题的，**不含 needs_human**，那些必须逐条处理）；需要审核口令，且个人令牌必须是发起这个模块生成请求的人。评审员有疑问的用例，批准时必须写备注，评审员的疑问和人的备注一起留在 `review_note` 里。`GET /api/modules/{id}/cases` 列出模块的用例、状态和备注。`/api/projects/{p}/cases` 的每条用例多了 `review_status`。
- **测试**：服务端 2 个集成测试（意见只是意见、别的节点不能代报、令牌不对 403、needs_human 批准要备注、一键批准只批 reviewed_ok、批准后才能执行、拒绝的不能执行、评审员没跑成全部转待人工确认）；节点 2 个端到端测试（复核成功入库、没有角色/输出不是 JSON/额度用完都转待人工确认）；agent 解析和提示词单元测试。
- **真实验证**（合成文档，一条来自文档、一条编造了「长按分享」）：Claude 7 秒、Gemini(agy) 38 秒，都判第一条 ok、第二条 needs_human 并说明「文档没有提到长按和分享」。只有这一个样本，不能当质量结论。
- **限制**：复核看不到截图（agy 的图片输入没验证，所以统一不给图），所以「预期和 UI 是否一致」只能靠人；评审员也是模型；前端复核列表还没做（第 5 步）。

## 个人令牌：记 30 天、页面上创建

- **为什么要个人令牌**：它证明「这个节点是你的」（规则 9）。局域网里多人共用一个平台，没有它任何人都能读你的角色配置、点检测消耗你的额度、用你的节点发任务；服务端靠它确认「发请求的人」和「节点的主人」是同一个人。
- **记 30 天**（`userToken.ts`）：令牌填完整（`u_` 开头加足够长）后记在本浏览器的 localStorage，带到期时间，到期读取时自动清掉；输到一半的不记；同一个令牌再填不续期；存储被禁用时退回「不记住」页面照常用；每处都有「忘记令牌」。角色页、新建任务（生成用例）、模块详情、发起测试四处共用。**只管个人令牌**——审核口令和 DeepSeek 的 API Key 仍然不落本地存储。这是用户明确选的（之前是只存内存，每次刷新都要重贴）。代价：令牌留在浏览器里，同一台电脑上别人能看到。
- **页面上创建**（`POST /api/users`）：之前只能命令行 `server create-user`。现在令牌输入框旁边有「创建个人令牌」，填名字、过审核口令（免得局域网里谁都能无限造身份）后创建；**令牌只显示这一次**（库里只存摘要，响应 `no-store`），可复制，可直接「使用这个令牌」；名字不能重复（409，且不会让已有令牌失效）。弹窗里说明：节点要属于这个令牌，启动节点时要设 `NODE_USER_TOKEN`。
- **一个容易踩的坑**：令牌只在**创建它的那个数据库**里有效。预览环境用的是临时库，你在开发库里创建的令牌它不认（401「需要有效的个人令牌」）。
- **测试**：令牌记忆 5 个（30 天、到期清掉、不完整不记、不续期、存储损坏或不可用）；创建弹窗 3 个（只显示一次、使用后记住、重复名字显示原因、没审核口令先弹口令框）；角色页刷新后不用再填；服务端接口 1 个（要口令、名字校验、令牌只存摘要、同名 409）。前端 64 个、全量 cargo test 通过。

## 身份改成「只记名字」（取代个人令牌；2026-11-23）

- **为什么改**：个人令牌太重——要创建、要贴、换库就失效，用户连着几轮卡在这。用户明确说了：数据是公用的、每个人都能看，也能用自己的额度跑别人的数据，**只是不能用别人的额度**；「测试人写成一个 ID，谁在跑就行了」。并且在「只记名字靠自觉」和「令牌对用户透明」之间选了前者。
- **怎么做**：节点启动设 `NODE_USER_NAME=你的名字`，服务端据此登记用户并绑定节点属主（`Hello.user_name`，老的 `NODE_USER_TOKEN` 仍兼容）；页面顶部填「我是谁」（请求头 `x-user-name`，中文做百分号编码），在本浏览器记 30 天，可清除。迁移 `0019`：`users.token_hash` 改成可空。节点列表多了「节点主人」，新增公开的名字列表 `GET /api/users`。
- **谁能做什么**：**查看公开**（角色、检测状态、应用检查结果、模块、用例、文档，不填名字也能看）；**改角色、检测（真调模型）、检查本机应用、用节点发任务、发起回归、批准自己发起的用例**要求名字对得上、且节点是你的。别人的数据你能用**自己的节点和额度**跑（测试钉住了：别人批准的用例我能跑、不能派到他的节点）。角色页和应用面板对非主人是只读，并说明为什么。
- **代价（如实写）**：名字不是机密，**任何人都能填别人的名字，系统不拦**，等于能用别人的节点、花别人的额度；规则 9 现在靠自觉，不再有技术保证。DeepSeek 的 API Key 不受影响（仍只在节点本机文件里，不上报、不回显）。如果以后局域网里不再是可信的人，要回到令牌或配对码。
- **删掉的**：页面创建令牌、令牌记 30 天、浏览器绑定（设备 Cookie，做了一半就弃用）。
- **文档去重**：项目只有一个（页面固定 `hafa`，不自动新建）；需求文档**内容相同就是同一份**——换行符统一、行尾空白去掉、去首尾空行后再按内容摘要去重，Windows 换行或行尾多个空格不会变成两份；行内空白算内容，不动。
- **没做**：管理员（主脑）聊天——新需求直接发给它、它自己读需求再分配任务。它要分配任务就会花额度，和之前选的「只聊天、只读」不一样，要先定它能做到哪一步（比如只能提议、要你点确认才派）。

## 管理员（后端和节点；前端页面下一步）

- **定位**：读项目的需求文档和各模块现状，和人聊天，**只提议，人点确认才执行**（用户的决定）。它没有任何工具、不能读文件、不能调接口、不能自己派任务、**不能批准用例**（批准一直是人的决定）。
- **是个角色**：配置里新增「管理员」岗位（`planner`），来源 Claude、Codex、agy 都行（纯文本）。回答由**提问人自己节点**上的管理员角色生成，用他自己的模型和额度（规则 9）；没有检测通过的管理员角色就如实说没有，不换别的。
- **流程**：`POST /api/admin/messages`（名字 + 审核口令）→ 服务端整理项目现状（最新需求文档、各模块和用例状态、已批准用例编号）连同最近 20 句对话发给节点 → 节点调模型 → 回答带提议回来 → 服务端**按库里的数据逐条核对提议**，通过的存成待确认卡片，核对不过的丢掉并在回答里说明 → 人在页面上点「确认」或「忽略」。同时只能问一句；超过 10 分钟没回音转成一条错误消息。对话按人存，别人看不到。
- **提议只有三种**（白名单，格式不对整条丢掉，最多 5 条）：`create_module` 新建模块；`generate_cases` 给模块生成用例（需要 UI 链接和区域截图，管理员拿不到，所以确认后只是打开预填好的表单，由人补上再提交）；`run_tests` 对**已批准**的用例发起测试（服务端核对模块和用例真的存在、已批准、可执行，不存在的编号去掉；全没有就丢掉这条）。
- **确认才执行**：`POST /api/admin/proposals/{id}/confirm`（名字 + 审核口令，只能是提议的主人）。先把待确认抢占成已确认（连点两次只会执行一次），再**重新核对一遍**（这段时间用例可能被拒绝了），然后用你的身份、在你的节点上执行：`run_tests` 建任务，用这个节点上检测通过的执行员和判定员角色（来源、模型都按角色配置，不写死）；节点不在线、节点已不是你的、角色没检测通过都如实失败并说明。`dismiss` 不执行任何东西。

## 页面创建名字（带密码）

- 「我是谁」旁新增「创建名字」：输入名字和密码，名字没被占就登记（`POST /api/users`，不需要复核口令）；重名 409，名字或密码（6 到 128 字符）不合格 400。

## 有密码的名字需要登录

- 创建名字后浏览器自动登录。已有密码的名字收到「请先登录」提示时，可以在「我是谁」旁打开登录弹窗。`POST /api/login` 返回的会话令牌按名字保存在浏览器，和服务端的会话一样有效 30 天。迁移 `0023_user_sessions.sql` 只存令牌的 SHA-256 摘要。点击「清除」会把会话从浏览器删除，并调用 `POST /api/logout` 注销服务端会话。
- 以有密码的名字执行操作时，请求需携带该用户的有效 `x-user-token`，缺失或失效返回 401。节点登记的无密码名字沿用原来的名字识别。角色和应用等公开数据仍可查看。
- 登录失败统一提示「名字或密码不对」。同一个名字连续失败 5 次后锁定 5 分钟，期间返回 429。管理员强制解除节点绑定仍直接验证管理员账号和密码，共用按名字记录的失败次数。

## 参数配置（P3：JSON 导入导出；2026-11-23）

- **导出**：`GET /api/configs/export`（所有人能看）返回 `{"types":[{name, code, remark, status, items:[{name, code, value, label, group_name, sort, remark, status}]}]}`，同时是导入文件的模板。

## 参数配置：节点取配置（2026-11-23）

- **协议**：新增 `ServerMsg::SetParams { device_retry, stuck_n, stuck_keep }`。服务端在 Welcome 之后发一次，配置变化（新增、修改、删除、导入）时广播给所有在线节点；离线节点下次上线时收到。节点不认识的消息会忽略，所以老节点不受影响。取值范围统一在 `protocol::SetParams::clamped` 里收：**重试 1 到 3 次（项目规则，配置写多大都不超过 3）**，卡住判定 2 到 10 次，保留记录数不小于判定次数、不超过 50。
- **服务端**：`configs::runtime_params` 读 `device_retry/max_attempts`、`stuck_detect/stuck_n`、`stuck_detect/keep` 三项；类型或配置项停用、没有、不是整数时该项用默认（3、3、6）。写入时已知配置就限制取值（重试 1–3、卡住判定 2–10、保留 2–50、岗位上限 1–20），不合理直接 400，导入时同样校验。
- **节点**：`crates/node/src/params.rs` 保存当前参数；收到 `SetParams` 后让本进程的设备层生效（`device::set_max_attempts`，硬上限仍是 3），并把 `HAFA_DEVICE_RETRY`、`HAFA_STUCK_N`、`HAFA_STUCK_KEEP` 作为环境变量传给之后启动的设备 MCP 服务。**已经在跑的那次执行不受影响，下一次执行才用新值。**
- **设备 MCP 服务**：卡住检测的阈值和保留条数改成可配置（`Guard::with_stuck`，最少 2 次；提示文字里的次数跟着配置）；设备层重试次数运行时可改（`device::set_max_attempts` / `max_attempts`）。步数上限、卡住检测、轨迹记录仍然在设备 MCP 服务里，不依赖模型自觉（规则 4）。
- **测试**：protocol 1 个（取值收进范围）；device 1 个（重试能配置但不超过 3，单独测试文件避免抢全局值）；mcp-device 1 个（阈值可配、最少 2 次、记录数）；node 1 个（应用参数并生成环境变量）；服务端 1 个（读配置、写入限制取值、写坏了读取时仍收进范围）。
