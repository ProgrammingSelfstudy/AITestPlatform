## 权限模型：不做登录页（必须遵守）

没有登录页或用户身份鉴权。没有共享口令只能查看；创建任务、取消执行和提交审核都需要同一个写入口令，不授予账号或节点权限：

1. 服务端默认只监听 `127.0.0.1`；局域网访问必须显式开启 `PLATFORM_ALLOW_LAN=1`，只能在可信内网使用。
2. `/api/nodes` 等接口暴露的是节点和设备清单（设备序列号、型号），不含账号凭证。
3. 审核记录、审核统计、脱敏训练样本和回放与其他只读页面一样在局域网可访问，不需要口令。**不开放账号信息接口**；账号凭证仍然只走「节点令牌 + 一次性」的接口，不经过前端。
4. 节点令牌（`NODE_TOKEN`）是节点接入的唯一凭证，必须显式配置，代码里不写默认值，不写日志。
5. 所有浏览器 POST 仍经过现有 Host / Origin / `X-Requested-With: ai-test-platform` / `Content-Type: application/json` 校验；开发代理保留浏览器 Host。创建、取消和审核提交在这之后还必须通过 `x-review-token` 校验。节点协议与本机 `server create-task` 不受影响。

## 其他取舍

- 模型来源只做本机会员（`claude` 命令行、`codex exec`），**不做 API Key 路径**，只留接口位；规划里 LiteLLM、mitmproxy 已换成 Rust 自研方案。
- 节点上报的 `vision` 来自技术验证里的实测，不是探测结果；是否已登录会员、额度够不够，要在 P0 后半段单独验证。
- 审核数据用于训练模型的路径尚未定（见 PoC 仓库规划九.8），先保证审核记录可导出成训练样本。

## P0 验证结论（2026-11-21）

| 验证项 | 结论 | 依据 |
|---|---|---|
| Rust 经 `claude` 命令行调 Claude 会员 | **可行** | `crates/agent` 的运行器对真实命令行跑通：非交互、流式输出（`stream-json`）、提示词走 stdin、剔除 `ANTHROPIC_*` / `OPENAI_*` 环境变量后仍走会员登录 |
| `rmcp` 起设备 MCP 服务 | **可行** | `rmcp 3.11.0`；真机上 `observe` 返回控件树文字 + 合法 PNG 截图；找不到元素明确报错、不乱点；没有 `HAFA_SERIAL` 拒绝启动 |
| 整条链路（claude 会员 → Rust MCP → 真机） | **可行** | 真实调用：模型只调用了 `observe`，读到锁屏页并如实说明截图全黑 |

**运行器已具备的能力**：卡住检测（超时没有任何输出就整组杀进程）、总时限、额度识别（命令行报错文案 + `rate_limit_event` 状态）、登录失效识别、异常退出带出原始 stderr、记录模型发起的工具调用、`--allowed-tools` 白名单。

**踩过的坑，别再踩**
- 杀进程要**杀整个进程组**：只杀 `claude` 本体，它拉起的 MCP 服务等子进程会残留并抓着管道，运行器会被拖住几十秒。
- 额度文案要允许 `your` 和 `limit` 之间夹一个词（weekly / daily），否则「reached your weekly limit」识别不出来。
- 节点与设备要在**事务**里一起写、一起读（快照），否则会出现「节点离线设备还空闲」「节点在线但没有设备」。
- 测试里不要执行新建的可执行文件（macOS 首次执行会被系统扫描，偶尔慢好几秒），用 `/bin/sh` 去读脚本。
- 读退出码不要经过管道（`cmd | tail` 拿到的是 `tail` 的）。
- sqlx 0.9 要求拼接出来的 SQL 显式标注 `AssertSqlSafe`；来自数据库的标识符先校验字符集再拼。

**Claude 会员额度（技术验证里一直没量化的数据）**：7 天窗口已用 **84%**（告警线 75%），2026-11-22 03:00（UTC+8）重置；5 小时窗口约 15%，没有开通超额。一次几百 token 的小调用约占 1 个百分点。开发期间真实调用要克制，测试优先用假的 `claude` 脚本。

**环境**：本机直连 npm / crates.io / Homebrew 的 ghcr 经常断流，已在项目内改用镜像（`.cargo/config.toml`、`web/.npmrc`，只影响本仓库，删掉两个文件即撤回）；PostgreSQL 17 用 Postgres.app（`~/Applications/Postgres.app`，数据在 `~/.local/var/postgresql@17`），开发库只监听本机。

**留给 P1 的已知事项**
- 设备 MCP 服务现在**没有护栏**（卡住检测、步数上限、高危页面返回 `need_human`、轨迹记录），所以只能用来验证链路，**不能当执行层用**。
- 锁屏时截图是黑的：执行前必须先唤醒并解锁（技术验证里 `setup_env` 的 `ensure_awake`）。
- 模型 / 角色配置、`codex exec` 运行器、看门狗对 GPT 链路的处理还没做。
- 登录鉴权仍未做（见上文约束）。

**`automation/hafa_automation`（Python，来自技术验证）**
- 改动只有三类：配置改读环境变量；账号改从 **stdin** 收（不读文件、不进命令行、不进环境变量、不打印）；输出改成 JSON 行事件。
- 契约：退出码 0 成功 / 1 某步失败（事件带当前页面文字）/ 2 用法错误 / 3 需要人工（屏幕解不开）/ 4 需要凭证。
- 账号标识用租约 id（不透明），脚本只用它判断手机上是不是已登录这个账号，不再用序号。

**`node::setup_runner`（Rust）**
- 凭证只经 stdin；转发任何输出前**在 Rust 侧再脱敏一次**（不把「脚本不会泄露」当前提）；环境变量清空后只放行基础变量和 `HAFA_*`；超时整组杀进程；`AccountArg` 的 `Debug` 不打印账号密码。
- 事件实时转发；退出码映射成 `Ok / StepFailed / NeedHuman / NeedCredentials / Usage / Crashed / Timeout`；退出码 0 但没有 `done` 事件、或既有 `error` 又退出 0，都不当成功。17 个测试。

### 已完成：用例导入与库表（`crates/server/src/cases.rs`、迁移 `0002`）

- **库表**：`projects`、`test_cases`（字段见 `docs/数据模型.md`，另加了 `platforms`、`refs`、`note`、`blocked_reason`）。库里有 check：`steps`、`expected` 不能为空数组。
- **导入是本机命令行，不是 HTTP 接口**：`server import-cases --dir <目录> [--project hafa] [--block 编号=原因]`。目前没有鉴权，一个能读服务器文件系统的接口等于任意文件读取；测试里专门验证了「不存在导入接口」。
- **强制的规则**（都有测试）：
  - 用例数据里账号相关的键（password / username / account / email / token / secret 等）必须是 `{{account.xxx}}` 占位符，写明文就拒绝导入，**错误信息里不回显值**（它很可能就是明文密码）；
  - **全有或全无**：任何文件有问题，一个都不导入，并且把**所有**问题一次报出来；库写入也在一个事务里，中途失败整体回滚（连项目一起）；
  - **幂等**：重复导入不改版本，只有内容真的变了才 `version + 1`（run 要靠版本号复现当时的用例）；只有状态变化（如解除受阻）不加版本；
  - **负例由 `level = 故意失败` 推出**，不靠编号后缀（TC-09 没有 `-F` 后缀也是负例）。
- **只读接口**：`GET /api/projects`、`/api/projects/{project}/cases`（按自然顺序，TC-10 在 TC-02 后面）、`/api/projects/{project}/cases/{code}`（带下发给节点的 `spec`）。
- **已用真实数据导入开发库**：PoC 的 16 个用例，5 条负例恰好是 PoC 里那 5 条，TC-07 标为受阻（房主不能下麦），库里没有明文账号字段；第二遍导入全部「无变化」。
- **做过变异检查**：把「内容变了才加版本」的比较条件改成永远为真，3 个测试失败；已还原。
- 导入**不能**用 `AppState::init`（它会把所有节点置离线），所以抽出了只跑迁移的 `server::migrate`。

**踩坑**：YAML 里没有「受阻」信息（PoC 是在批跑脚本里排除了 TC-07），所以导入时要用 `--block` 显式指定。

- **设备占用锁**：部分唯一索引 `runs_device_lock`，同一台设备同一时刻只有一个活跃 run。`node_lost`（节点掉线宽限期内）也占着设备，否则节点重连前别的排队任务会把手机领走，想续跑时设备已被占。
- **Judge 没跑成时最终结果只能是「待确认」**：check 约束，不能用执行员的自评顶替。
- **blocked 必须有原因**：统计完成率要区分链路 / 环境故障。
- `finished` 的最终结果不能是 blocked。

**应用层的规则**
- **run 创建时就绑定到一个节点**，只有这个节点的连接能领走、推进它：「谁发起谁付额度、不能委派」是靠**结构**保证的（不存在跨节点调度这个动作），不靠校验发起人，因为现在没有登录。创建任务时还校验所选节点真的有所选的模型来源。节点操作别的节点的 run，一律拒绝，且一次都不生效。
- **用例内容快照进 run**：排队期间用例被改了，这次执行仍用创建时的内容，能复现。
- **最终结果由服务端按逐条判定重新算，不信节点报的**：有 failed 就是 failed；没有 failed 但有 uncertain、判定条数和预期条数对不上、或有重复 / 越界的编号，就是 uncertain；只有全部 passed 且恰好覆盖每一条预期才是 passed。**漏判的预期不能被当成通过。**
- **节点掉线**：执行 / 判定中的 run 转 `node_lost`，**不直接判失败**；还没开始的退回排队。**节点重连**时服务端对它声称仍在跑的 run 按宽限期决定继续还是放弃（已有执行员结果的回到判定阶段）；服务端以为在跑、节点却没有的（节点重启丢了本地进度）判受阻，并释放设备。
- 节点心跳里的设备状态**不能覆盖**有活跃 run 的设备（服务端说了算：busy）。
- 领取用 `FOR UPDATE SKIP LOCKED`，10 个并发领取 5 个 run、3 台设备，恰好领走 3 个，没有重复。
- 非法状态流转明确报错，不静默忽略。

**测试**：状态机纯逻辑 8、数据库 28、WebSocket 联动 6。**做过变异检查**：去掉设备 busy 保护 → 2 个测试失败；重连时不管宽限期 → 1 个失败；已还原。

**踩坑（真实 bug，测试抓到的）**：同一任务的多个 run 在同一个事务里创建，`queued_at`（事务开始时间）完全相同，排序退化成按随机 UUID，**任务内的执行顺序是乱的**。改用单调递增的 `seq` 列排队，并加了「20 个 run 严格按创建顺序领取」的回归测试。

**还没做**：把状态机接到 WebSocket 派发（服务端主动给节点发 `run_assign`、收 `step` / `executor_done` / `judge_done` 等并落库）、宽限期过期的定时清理（`expire_node_lost` 已实现，还没有定时调用它）、取消时通知节点、创建任务的入口（目前只有库函数，没有 HTTP 接口，也没有命令行）。

### 人工审核、录屏回放和训练导出
