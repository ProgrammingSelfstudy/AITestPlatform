## 权限模型：不做登录页（必须遵守）

没有登录页或用户身份鉴权。没有共享口令只能查看；创建任务、取消执行和提交审核都需要同一个写入口令，不授予账号或节点权限：

1. 服务端默认只监听 `127.0.0.1`；局域网访问必须显式开启 `PLATFORM_ALLOW_LAN=1`，只能在可信内网使用。
2. `/api/nodes` 等接口暴露的是节点和设备清单（设备序列号、型号），不含账号凭证。
3. 审核记录、审核统计、脱敏训练样本和回放与其他只读页面一样在局域网可访问，不需要口令。**不开放账号信息接口**；账号凭证仍然只走「节点令牌 + 一次性」的接口，不经过前端。
4. 节点令牌（`NODE_TOKEN`）是节点接入的唯一凭证，必须显式配置，代码里不写默认值，不写日志。
5. 所有浏览器 POST 仍经过现有 Host / Origin / `X-Requested-With: ai-test-platform` / `Content-Type: application/json` 校验；开发代理保留浏览器 Host。创建、取消和审核提交在这之后还必须通过 `x-review-token` 校验。节点协议与本机 `server create-task` 不受影响。

## 其他取舍

- 模型来源只做本机会员（`claude` 命令行、`codex exec`），**不做 API Key 路径**，只留接口位；规划里 LiteLLM、mitmproxy 已换成 Rust 自研方案。
- 节点上报的 `vision` 来自技术验证里的实测，不是探测结果；是否已登录会员、额度够不够，要在 P0 后半段单独验证。
- 审核数据用于训练模型的路径尚未定（见 PoC 仓库规划九.8），先保证审核记录可导出成训练样本。

## P0 验证结论（2026-11-21）

| 验证项 | 结论 | 依据 |
|---|---|---|
| Rust 经 `claude` 命令行调 Claude 会员 | **可行** | `crates/agent` 的运行器对真实命令行跑通：非交互、流式输出（`stream-json`）、提示词走 stdin、剔除 `ANTHROPIC_*` / `OPENAI_*` 环境变量后仍走会员登录 |
| `rmcp` 起设备 MCP 服务 | **可行** | `rmcp 3.11.0`；真机上 `observe` 返回控件树文字 + 合法 PNG 截图；找不到元素明确报错、不乱点；没有 `HAFA_SERIAL` 拒绝启动 |
| 整条链路（claude 会员 → Rust MCP → 真机） | **可行** | 真实调用：模型只调用了 `observe`，读到锁屏页并如实说明截图全黑 |

**运行器已具备的能力**：卡住检测（超时没有任何输出就整组杀进程）、总时限、额度识别（命令行报错文案 + `rate_limit_event` 状态）、登录失效识别、异常退出带出原始 stderr、记录模型发起的工具调用、`--allowed-tools` 白名单。

**踩过的坑，别再踩**
- 杀进程要**杀整个进程组**：只杀 `claude` 本体，它拉起的 MCP 服务等子进程会残留并抓着管道，运行器会被拖住几十秒。
- 额度文案要允许 `your` 和 `limit` 之间夹一个词（weekly / daily），否则「reached your weekly limit」识别不出来。
- 节点与设备要在**事务**里一起写、一起读（快照），否则会出现「节点离线设备还空闲」「节点在线但没有设备」。
- 测试里不要执行新建的可执行文件（macOS 首次执行会被系统扫描，偶尔慢好几秒），用 `/bin/sh` 去读脚本。
- 读退出码不要经过管道（`cmd | tail` 拿到的是 `tail` 的）。
- sqlx 0.9 要求拼接出来的 SQL 显式标注 `AssertSqlSafe`；来自数据库的标识符先校验字符集再拼。

**Claude 会员额度（技术验证里一直没量化的数据）**：7 天窗口已用 **84%**（告警线 75%），2026-11-22 03:00（UTC+8）重置；5 小时窗口约 15%，没有开通超额。一次几百 token 的小调用约占 1 个百分点。开发期间真实调用要克制，测试优先用假的 `claude` 脚本。

**环境**：本机直连 npm / crates.io / Homebrew 的 ghcr 经常断流，已在项目内改用镜像（`.cargo/config.toml`、`web/.npmrc`，只影响本仓库，删掉两个文件即撤回）；PostgreSQL 17 用 Postgres.app（`~/Applications/Postgres.app`，数据在 `~/.local/var/postgresql@17`），开发库只监听本机。

**留给 P1 的已知事项**
- 设备 MCP 服务现在**没有护栏**（卡住检测、步数上限、高危页面返回 `need_human`、轨迹记录），所以只能用来验证链路，**不能当执行层用**。
- 锁屏时截图是黑的：执行前必须先唤醒并解锁（技术验证里 `setup_env` 的 `ensure_awake`）。
- 模型 / 角色配置、`codex exec` 运行器、看门狗对 GPT 链路的处理还没做。
- 登录鉴权仍未做（见上文约束）。

**`automation/hafa_automation`（Python，来自技术验证）**
- 改动只有三类：配置改读环境变量；账号改从 **stdin** 收（不读文件、不进命令行、不进环境变量、不打印）；输出改成 JSON 行事件。
- 契约：退出码 0 成功 / 1 某步失败（事件带当前页面文字）/ 2 用法错误 / 3 需要人工（屏幕解不开）/ 4 需要凭证。
- 账号标识用租约 id（不透明），脚本只用它判断手机上是不是已登录这个账号，不再用序号。

**`node::setup_runner`（Rust）**
- 凭证只经 stdin；转发任何输出前**在 Rust 侧再脱敏一次**（不把「脚本不会泄露」当前提）；环境变量清空后只放行基础变量和 `HAFA_*`；超时整组杀进程；`AccountArg` 的 `Debug` 不打印账号密码。
- 事件实时转发；退出码映射成 `Ok / StepFailed / NeedHuman / NeedCredentials / Usage / Crashed / Timeout`；退出码 0 但没有 `done` 事件、或既有 `error` 又退出 0，都不当成功。17 个测试。

### 已完成：用例导入与库表（`crates/server/src/cases.rs`、迁移 `0002`）

- **库表**：`projects`、`test_cases`（字段见 `docs/数据模型.md`，另加了 `platforms`、`refs`、`note`、`blocked_reason`）。库里有 check：`steps`、`expected` 不能为空数组。
- **导入是本机命令行，不是 HTTP 接口**：`server import-cases --dir <目录> [--project hafa] [--block 编号=原因]`。目前没有鉴权，一个能读服务器文件系统的接口等于任意文件读取；测试里专门验证了「不存在导入接口」。
- **强制的规则**（都有测试）：
  - 用例数据里账号相关的键（password / username / account / email / token / secret 等）必须是 `{{account.xxx}}` 占位符，写明文就拒绝导入，**错误信息里不回显值**（它很可能就是明文密码）；
  - **全有或全无**：任何文件有问题，一个都不导入，并且把**所有**问题一次报出来；库写入也在一个事务里，中途失败整体回滚（连项目一起）；
  - **幂等**：重复导入不改版本，只有内容真的变了才 `version + 1`（run 要靠版本号复现当时的用例）；只有状态变化（如解除受阻）不加版本；
  - **负例由 `level = 故意失败` 推出**，不靠编号后缀（TC-09 没有 `-F` 后缀也是负例）。
- **只读接口**：`GET /api/projects`、`/api/projects/{project}/cases`（按自然顺序，TC-10 在 TC-02 后面）、`/api/projects/{project}/cases/{code}`（带下发给节点的 `spec`）。
- **已用真实数据导入开发库**：PoC 的 16 个用例，5 条负例恰好是 PoC 里那 5 条，TC-07 标为受阻（房主不能下麦），库里没有明文账号字段；第二遍导入全部「无变化」。
- **做过变异检查**：把「内容变了才加版本」的比较条件改成永远为真，3 个测试失败；已还原。
- 导入**不能**用 `AppState::init`（它会把所有节点置离线），所以抽出了只跑迁移的 `server::migrate`。

**踩坑**：YAML 里没有「受阻」信息（PoC 是在批跑脚本里排除了 TC-07），所以导入时要用 `--block` 显式指定。

- **设备占用锁**：部分唯一索引 `runs_device_lock`，同一台设备同一时刻只有一个活跃 run。`node_lost`（节点掉线宽限期内）也占着设备，否则节点重连前别的排队任务会把手机领走，想续跑时设备已被占。
- **Judge 没跑成时最终结果只能是「待确认」**：check 约束，不能用执行员的自评顶替。
- **blocked 必须有原因**：统计完成率要区分链路 / 环境故障。
- `finished` 的最终结果不能是 blocked。

**应用层的规则**
- **run 创建时就绑定到一个节点**，只有这个节点的连接能领走、推进它：「谁发起谁付额度、不能委派」是靠**结构**保证的（不存在跨节点调度这个动作），不靠校验发起人，因为现在没有登录。创建任务时还校验所选节点真的有所选的模型来源。节点操作别的节点的 run，一律拒绝，且一次都不生效。
- **用例内容快照进 run**：排队期间用例被改了，这次执行仍用创建时的内容，能复现。
- **最终结果由服务端按逐条判定重新算，不信节点报的**：有 failed 就是 failed；没有 failed 但有 uncertain、判定条数和预期条数对不上、或有重复 / 越界的编号，就是 uncertain；只有全部 passed 且恰好覆盖每一条预期才是 passed。**漏判的预期不能被当成通过。**
- **节点掉线**：执行 / 判定中的 run 转 `node_lost`，**不直接判失败**；还没开始的退回排队。**节点重连**时服务端对它声称仍在跑的 run 按宽限期决定继续还是放弃（已有执行员结果的回到判定阶段）；服务端以为在跑、节点却没有的（节点重启丢了本地进度）判受阻，并释放设备。
- 节点心跳里的设备状态**不能覆盖**有活跃 run 的设备（服务端说了算：busy）。
- 领取用 `FOR UPDATE SKIP LOCKED`，10 个并发领取 5 个 run、3 台设备，恰好领走 3 个，没有重复。
- 非法状态流转明确报错，不静默忽略。

**测试**：状态机纯逻辑 8、数据库 28、WebSocket 联动 6。**做过变异检查**：去掉设备 busy 保护 → 2 个测试失败；重连时不管宽限期 → 1 个失败；已还原。

**踩坑（真实 bug，测试抓到的）**：同一任务的多个 run 在同一个事务里创建，`queued_at`（事务开始时间）完全相同，排序退化成按随机 UUID，**任务内的执行顺序是乱的**。改用单调递增的 `seq` 列排队，并加了「20 个 run 严格按创建顺序领取」的回归测试。

**还没做**：把状态机接到 WebSocket 派发（服务端主动给节点发 `run_assign`、收 `step` / `executor_done` / `judge_done` 等并落库）、宽限期过期的定时清理（`expire_node_lost` 已实现，还没有定时调用它）、取消时通知节点、创建任务的入口（目前只有库函数，没有 HTTP 接口，也没有命令行）。

### 人工审核、录屏回放和训练导出

### 证据文件地址签名、判定前登录检查、前端改版（2026-11-21）

### P3 第一步：脚本归档层（2026-11-21）

分期建议里 P3 的前提是「候选合规才入库，自检通过才归档，按用例版本记录来源执行、脚本版本和内容摘要」。生成核心此前只到内存产物为止，没有任何存储。这一步补上存储、版本和状态流转，**不含**自检执行、平台入口和零模型回归，那些还没做。

**库表 `scripts`**（迁移 `0012`）。字段：用例、版本（用例内从 1 递增）、依据的用例版本、来源执行、文件表（路径到源码）、内容摘要、生成时的模型来源／名称／强度、状态与状态说明。库层约束兜底：状态取值、摘要为 64 位十六进制、文件表必须是非空对象、模型来源只能是 `claude_cli` 或 `codex_exec`、同用例同版本唯一、同用例同内容唯一。绕过模块直接写库写不进这些脏数据，有测试覆盖。

**归档模块 `crates/server/src/scripts.rs`**。服务端不依赖 `agent`，所以不重复做静态校验，也不声称校验过脚本内容里有没有凭证，那由生成端的 `scriptcheck` 负责。入库前服务端再做一遍不依赖模型的硬检查，任何一条不满足都拒绝，且不留记录：

- 来源执行必须属于这个用例，用例版本和当前一致（用例改版后，旧版本的执行不能生成新脚本），Judge 已完成，最终结果为通过，且每条预期都有通过的判定项。待人工确认、失败、受阻都不能生成脚本。
- 文件名白名单与 `scriptcheck` 规则 0 一致：必须有 `test_<编号>.py`，可选 `pages/<编号>_pages.py`，别的一律不收；最多 6 个文件，单个不超过 64 KiB，不能为空，不含 NUL。
- 生成端给的单文件摘要，服务端按原始 UTF-8 内容重算比对，少一个或错一个都拒绝，并指出是哪个文件。
- 整套内容摘要 = 按路径排序，把「路径、NUL、单文件摘要、换行」逐个连起来取 SHA-256。同用例同样内容只归档一次，重复提交返回已有版本。
- 先锁住用例行再分配版本号，并发归档同一用例不会重复或跳号（6 路并发有测试）。

**状态只能顺着走**：候选 → 自检通过 → 获准 → 下线。候选和自检通过都可以被拒绝，获准后只能下线，拒绝和下线是终点；**不允许跳过自检直接获准**，也不允许回退。失败的迁移不改状态。

**验收**。全工作区 35 个套件、523 个用例通过，0 失败，无新增警告；新增 5 个单元测试（文件名、摘要、状态机）和 13 个数据库测试。

**没做、需要注意**
- 这一步没有 HTTP 接口（第二步已补，见下节）、没有页面，也没有自检执行：「自检通过」目前只是一个状态值，**还没有任何代码会真的去跑自检并改状态**。
- 生成核心还没有接到归档上：`scriptgen_dev` 仍然只输出到标准输出，没有人把它的产物写进 `scripts`。
- TC-04 候选脚本的断言缺口（见上一节）仍然没有补，所以它不能走到获准。
- 常驻的开发库要等服务端下次启动时才会执行迁移 `0012`，目前没有接口用到这张表，所以没有影响。

**发现并修复两个缺陷**：

1. **带账号租约的真机执行必然失败（审计消耗了一次性脱敏清单）。** 执行员启动前有一步「审计」，它用和真实会话同一套 MCP 配置启动一次设备服务来读工具清单；设备服务读完脱敏清单文件就立即删除（这是有意设计，明文不能留盘）。审计在前，把文件消耗掉，真实会话再启动设备服务时读不到清单，在回复 initialize 之前就退出。已手动复现：连续两次用同一路径启动，第二次报 `读取脱敏清单失败：No such file or directory`。此前没有发现，是因为所有测试都用假设备。修法：新增 `build_audit_args`，审计参数与真实运行一致，**只是不带脱敏清单**（审计只列工具、不执行动作）；真实会话仍完整带上，没有放宽「读完即删」。环境变量名抽成共用常量 `SECRETS_ENV`，避免节点和 agent 两处字符串漂移。
2. **规则 7 没做到：原始错误被丢掉。** Codex 异常退出时 `Summary` 里其实已经记着 stderr 尾部和退出码，但节点拼受阻原因时没用，页面上只有一句空话。现在「没有给出结论」和「没有留下轨迹」两条路径都带上原始错误和退出码，没有错误输出就如实写「没有错误输出」，拿不到退出码写「未知」。

两处都先写了会失败的回归测试再修。

**第 4 次跑通**：15 步、32 次工具调用、用时 352 秒，执行员 `gpt-6.2-astra`（强度 max）。执行员自评「待确认」，Judge 独立判定 **5 条预期全部通过**，每条都有引用截图和页面文字的具体证据，最终结果「通过」；两者不一致正是「独立判定、不依赖执行员自评」在起作用。随后 `node gen-script` 用任务里 Judge 角色配置的模型（`claude-sonnet-5-5`，来自配置，不是写死的）生成并归档为**版本 1，状态候选**。

**对生成脚本的评价**（静态校验通过不等于脚本好用）：
- 好的一面：这次有真实的 15 步轨迹，脚本贴着实际流程（滑到底、回滑找目标歌曲、点勾选框、`Add(1)`、「Music added successfully」、`Music(1/50)`），5 条预期各有断言，不再是上一轮那样按 `ui_map` 编的。
- **预期 3「选择框变为勾选」仍然没有被独立验证**：`select_target()` 点完就返回 `True`，不看勾选状态，只靠 `Add(1)` 文字间接推断。这就是此前文档里记过的 TC-04 断言缺口，**没有补上**。
- **大量写死的屏幕坐标**：`tap_xy(295, 1527)`、`xy=(361, 1532)`、`xy=(570, 1532)`、勾选框 `x=71`，只在 720×1600 的这台机器上成立，换分辨率或底部导航栏不同的机型会点偏。模型的备注只承认了勾选框这一处。
- 脚本里 `from generated.pages.tc04_pages import …` 假设了包的目录结构，是否和执行层布局一致没有验证。
- **这个脚本没有在真机上自检过**，所以不能获准。

**偶发失败的测试**：全量并行时 `agent` 的 `codex_run` 里有两个靠时间窗口判断的测试出现过偶发失败（`工具调用挂住_判tool_hang再续跑`、`need_human期间不算卡住`），都是单独连跑通过，机器上同时跑着服务端、节点、前端和数据库时更容易出现。没有查根因，也没有改。

**仍然没做**：自检的真正执行（把候选在真机上跑一遍，再决定自检通过或拒绝）；补预期 3 的勾选断言；去掉写死坐标；平台入口按版本回归；获准和下线的接口与页面。

## P3 · 脚本坐标规则、重新生成与真机自检

**生成端补强**：校验新增规则 10，`ui.tap_xy` 的 x、y 和 `ui.tap(..., xy=...)` 不能是纯数字常量，必须由 `ui.find` 找到的元素位置推出（`*变量` 展开字面元组的写法看不出来，是已知缺口，写在代码注释里）。提示词补了两条：坐标由相邻元素推出；状态类预期要在动作后重新读页面状态再断言，读不到依据就在备注里写明是间接推断。用同一次通过的执行重新生成，得到**版本 2**：坐标改为由元素位置推出，预期 3 仍只能靠 `Add(1)` 出现、`Add(0)` 消失间接推断（勾选框没有独立文案），备注如实写了。勾选框的偏移 `left + 71` 仍是常量，换密度不同的机型可能点偏。

**自检的真正执行**（`node self-check <脚本编号> [--serial]`，不花模型额度，会占用手机）：
- 服务端新增两个节点认证接口，都要求脚本来源于调用的节点：`GET /api/scripts/{id}/files` 取源码和用例编号；`PUT /api/scripts/{id}/self-check` 回报结果，候选通过变「自检通过」、失败变「已拒绝」并记下原因，其他状态返回 409。回报用 PUT 而不是 POST：全局的浏览器写保护会拦掉不带浏览器头的 POST，节点的写接口都用 PUT。
- 节点把脚本写成 `generated/` 包（含 `__init__.py` 和 `pages/__init__.py`），用 `python -m pytest -p hafa_automation.pytest_plugin` 在手机上跑，超时杀整个进程组，临时目录跑完即清。
- **脚本缺陷与环境问题分开**：脚本自己失败才拒绝；前置状态或关房失败、超时、手机连不上只报错，脚本保持候选，不能因为手机掉线把好脚本判死。拒绝时把 pytest 原始输出末尾记进状态说明（规则 7）。
- **没有账号租约**：自检假定手机上已登录好目标账号（`--skip-login`）。节点进程和自检命令是两个进程，设备锁不跨进程，所以要人确认节点没有在这台手机上跑任务。
- 测试：6 个端到端用例（真服务端和数据库，假 python 模拟 pytest 的通过、失败、环境问题、超时、重复自检、非来源节点）、3 个服务端 HTTP 用例；变异检查：让环境问题判断失效，对应用例失败。全量 554 个用例通过。

**第一次真机自检结果：版本 2 被拒绝，拒绝是对的。** 脚本先把列表滑到末尾，再调 `scroll_down_to` 向下滑（往顶部方向）去找目标歌曲，目标在末尾，往回滑 10 次回到列表顶部也没找到，断言「找到 tst_swipe_zz」失败。前 5 条断言（含滑到底）都通过了。这是生成脚本的真实缺陷：模型没理解「已经滑到末尾，目标就在当前屏」，静态校验不可能发现，只有真机跑才暴露。

**仍然没做**：失败原因回灌给生成（目前生成只对静态校验违规重试，不对运行失败重试）；预期 3 的勾选断言；获准和下线的接口与页面；平台入口按版本回归；自检不领账号租约，手机必须已登录。

## P3 · 按自检失败修正，版本 3 自检通过

**失败回灌**：`node gen-script <run> --fix-from <被拒绝的脚本编号>`。生成输入多一个 `previous_attempt`（上一版源码加 pytest 原始失败输出，一并脱敏），提示词要求先对照轨迹判断真实失败原因、只修这个原因、保留已通过的部分、在备注里写明原因和修法。节点在调用模型**之前**检查：要修正的脚本必须是本节点的、状态是已拒绝、有失败输出、与这次执行是同一个用例，否则不花额度。修正后是新版本，不覆盖旧版本。服务端的取源码接口新增 `status_note` 字段。测试：3 个节点端到端用例（带上失败输出和源码、没有修正模式时不带、条件不满足不调模型），全量 557 个通过。

**真实结果**：用同一次通过的执行加版本 2 的失败输出生成**版本 3**，真机自检 **通过**（69.85 秒，1 passed），状态变为「自检通过」。模型的诊断是对的：上一版用 `ui.find(目标)` 判断目标出现，而 `find` 默认精确匹配，列表行的文案是 `tst_swipe_zz / 00:30`，所以永远找不到；版本 3 改用按可见文案包含匹配的 `ui.has` 判断，选中时先 `find`，找不到再从完整文案里取出做精确查找。我最初把版本 2 的失败理解成滑动方向错了，**这个判断是错的**，是模型靠失败输出和轨迹对照出来的真实原因。

三个版本的走向：版本 1 带写死坐标（不再能通过校验，仍是候选），版本 2 被自检拒绝，版本 3 自检通过。**自检通过不等于获准**：获准要人来决定，而且还没有获准的接口和页面。

**还要知道**：
- 版本 3 的预期 3（勾选）仍只能靠 `Add(1)` 出现、`Add(0)` 消失间接推断，备注里写明了。
- 自检只跑了一次，没有测稳定性；单次通过不代表不会偶发失败。
- 全量跑 `cargo test --workspace` 时 `server/tests/accounts.rs` 的 `导入设备字段覆盖命令行_重导更新绑定且只输出数量` 偶发失败过一次，单独重跑和整体重跑都通过，没有查根因。

## P3 · 获准、下线与「回归脚本」页面

**服务端**（人的决定，用审核口令，和创建任务、提交审核同一套；节点令牌不能替人决定）：
- `POST /api/scripts/{id}/approve | retire | reject`，请求体 `{note}`。获准的原因可不写，下线和拒绝必须写（最多 300 字）。
- 状态机在 `scripts::transition`：不能跳过自检直接获准；**同一用例同时只能有一个获准版本**（先下线旧的才能获准新的，并发时由迁移 `0013` 的部分唯一索引兜底）；**用例内容变过的旧脚本不能获准**（脚本依据的用例版本必须等于用例现在的版本）；获准后只能下线，拒绝和下线是终点，不能恢复。获准前锁住用例行，两个脚本同时获准会串行化。
- 人的决定追加在状态说明后面，不覆盖自检输出；总长不超过库里的 2000 字上限，放不下时截掉旧输出的开头、保留末尾和完整原因。
- `GET /api/projects/{project}/scripts`：项目里所有脚本版本，带用例编号和标题，不含源码。

**顺手修了一个会在真实输出变长时才出现的缺陷**：库里 `status_note` 限 2000 字，而自检回报最多允许 3500/4000 字，输出一长就会在写库时失败。之前的测试用的都是短输出，没发现。现在节点只留 1500 字末尾，服务端对自检输出的上限收紧到 1800 字，超出直接 422，而不是写库时才报错。

**前端**：新增「回归脚本」页（`#/scripts`）：按用例、版本列出全部脚本；状态用标签区分（候选待自检、自检通过待获准、已获准、已拒绝、已下线）；展开能看文件、依据的用例版本、生成备注和状态说明；按状态只显示可用的按钮（候选只能拒绝，自检通过可获准或拒绝，已获准可下线），点开填原因，再输入审核口令。按钮只决定显示，真正的规则在服务端。「已获准」用绿色标签，页面说明里写明它只表示可被平台选来回归，不是测试通过。

**验证**：服务端 12 个新增用例（完整流程、不能跳过自检、一用例一个获准、用例变过不能获准、拒绝和下线要原因、令牌与节点令牌、长输出不超限、按项目列出）加状态说明截断的单元测试；变异检查：去掉「用例版本没变」和「另一个获准版本」两道检查，对应两个用例失败。全量 565 个通过。页面在浏览器里用真实数据看过：三个版本、展开详情、获准对话框都正常；**没有在真实库里点确认**，版本 3 仍是「自检通过」，获准是你的决定。

**仍然没做**：平台按版本回归（选已获准的版本，在节点上跑）；前端没有自动化测试（项目里本来就没有前端测试脚本，页面只做了类型检查、构建和浏览器里的手工检查）；自检不领账号租约；预期 3 的勾选仍是间接推断。

## P3 · 按版本回归，以及 accounts 测试的真实根因

**回归**（`node regress <用例编号> [--project hafa] [--serial …]`，不花模型额度，会占用手机）：
- 取该用例当前**已获准**的脚本版本（`GET /api/projects/{project}/cases/{code}/approved-script`，没有获准版本就 404，节点在占用手机之前就报错），在本节点真机上用 pytest 跑，结果记到新表 `script_regressions`（迁移 `0014`），页面「回归脚本」新增「最近回归」列，展开能看原始输出。
- **失败是回归的结论**：如实记下通过或失败和原始输出，**不改脚本状态**，也不自动下线。失败可能是产品退化，也可能是脚本随界面改版失效，需要人判断。
- **环境问题不记**：设备掉线、前置状态或关房失败、超时只报错。把手机掉线记成「回归失败」会让人误以为产品退化。
- **获准的脚本是项目资产**：不要求脚本来自本节点，任何认证节点都可以在自己的设备上回归，结果记在回报的节点名下。只有已获准的版本能记（候选、自检通过、已拒绝、已下线都返回 409）。
- 自检和回归共用同一套「写成 generated 包、跑 pytest、识别环境问题」，只是后续处理不同：自检的失败会拒绝候选，回归的失败只是记录。
- 测试：服务端 3 个 HTTP 用例（取已获准版本、只能记在已获准版本上且页面带最近一次、格式与认证），节点端 6 个端到端用例（通过、失败是结论、环境问题和超时不记、没有获准版本不占手机、下线后用新版本、别的节点也能回归）；变异检查：让回归把任何结果都当通过，失败用例报错。

**这次没有做的：在平台页面上点按钮发起回归。** 现在回归由节点命令行触发，结果上报到平台并显示；页面发起要走任务派发那一整套（派发给节点、节点领取、取消、状态），是另一个独立的功能，没有在这一步里做。

**真实根因：`server/tests/accounts.rs` 的 `导入设备字段覆盖命令行_重导更新绑定且只输出数量`。** 前面我把它记成「偶发失败，没查根因」，这是不对的：迁移加到 14 个之后它在全量并行下稳定复现（连续 3 次）。先把子进程的 stdout 带进断言消息，看到的是：多个测试并行迁移同一个库，抢 `pg_advisory_lock` 等了 1.46 秒，超过 sqlx 的慢语句阈值（1 秒），sqlx 打了一条警告；而服务端把**日志写在 stdout 上**，混进了 `import-accounts` 本该只输出的「已导入 2 个账号」。两处修复：服务端日志改写 stderr（stdout 留给命令输出，对所有子命令都成立，这是设计上的修正，不只是为了测试）；测试的日志级别改成 `warn,sqlx::query=error`，排除与被测行为无关的慢查询警告，其他警告仍保留，所以「不泄露账号」的检查没有被放宽。修复后连续 3 次全量并行 574 个全部通过。

**另一个偶发仍未查**：`agent/tests/codex_run.rs` 里 `need_human期间不算卡住` 这次全量里又失败过一次，单独跑通过，是靠时间窗口判断的测试，机器上同时跑着服务端、节点、前端和数据库时容易触发；没有改。
