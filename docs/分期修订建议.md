# 分期修订建议

以 `~/Documents/code/AIAutomation/docs/AI测试平台规划.md` 第十三章和本仓库 [落地记录](落地记录.md) 为依据（2026-11-21）。落地记录中，录屏、审核与导出归入 P2，Python 脚本运行时和生成核心归入 P3；这些小节的位置不等于阶段已验收。本文只建议调整顺序和验收范围，不改技术选型或原规划。

## 一、现状与原规划的差异

| 原规划 | 落地记录所见 | 建议调整 |
|---|---|---|

## 二、建议顺序与逐期验收

**先收口 P0 可行性 → P1 Android 执行 → P2 审核与恢复 → P3 脚本回归；再排 Web／接口与需求流程、iOS 与扩面、治理与分享。** 以下放行标准为建议，不代表本次已验证。

### P0：证明会员登录到设备的最小链路

- **已有证据（历史记录）**：Claude 会员命令行经 Rust 设备 MCP 在 Android 上调用了 `observe`，返回控件树及截图；只观察了锁屏页，不能据此宣称用例可执行或 GPT 链路已过。GPT 工具审计和真机执行的证据在 P1。
- **放行口径**：至少一条本机会员链路有可回查的只读观察记录，工具与设备绑定正确，缺设备配置明确拒绝；用替身覆盖未登录、额度耗尽、无输出超时等异常，给出可追查的原因并停住，不转 API Key、不换节点或模型来源。P0 不以完整用例通过为目标。

### P1：跑通 Android 执行与独立判定

- **已有证据（历史记录）**：导入 16 条 PoC 用例，其中 5 条故意失败、TC-07 标受阻。TC-04 有从页面发起到逐条判定的端到端记录；TC-04／TC-02 双机并行各用绑定账号，结束后租约释放。文字证据复测时，5 条负例为 4 条失败、1 条待确认（TC-09 控件树连续为空），无误通过。
- **放行口径**：至少一个代表正例从任务创建、同节点派发、准备、实时步骤／证据到独立 Judge、结果落库和收尾全通。通过须逐条覆盖且有实际查阅的截图或步骤文字；明确不匹配即失败，漏判或证据不足标待人工确认，环境阻塞单列。5 条负例以 **0 误通过**为红线，待确认必须有缺证原因和补证项，不计作判定正确。高危动作在工具层拒绝并返回 `need_human`；卡住、步数上限与轨迹由设备 MCP 负责。
- **放行口径**：两台设备可同时执行且无串账号、重复占机、跨节点领取；取消或异常也能收回设备与租约。凭证只向绑定节点一次性交付、运行时注入，其他环节保留 `{{account.xxx}}` 占位，日志、轨迹、报告及浏览器响应均无明文。角色使用任务配置，发起人只使用自己的节点和会员额度。试点若需要强制换号登录（`force_login`），须补真机证据，不能用已登录复用替代；文字输入不阻塞现有样本，纳入需输入的用例前再验。

### P2：让证据可复核，验证故障恢复

- **已有证据（历史记录）**：录屏在准备完成后开始、收尾前结束，已记录分段回放、按步骤定位、人工标注与脱敏导出；录屏不参与 Judge。审核的 3 项 PostgreSQL 集成检查在沙箱连接阶段被拒，不能计为通过；未记录录屏留存清理任务。
- **放行口径**：用一条多段录屏与一条缺时间索引的记录验收连续播放、按步跳转和不可定位提示。在可连接数据库的授权环境验证审核写入、历史／统计与样本导出，原始 Judge 和人工标注可分别追查。创建、取消、审核三项写入验证同一口令，未授权拒绝、错口令限流不影响只读。导出不含凭证、序列号、证据路径、链接或文件；无法核对脱敏则拒绝。定下录屏访问边界、留存时长、容量上限和清理责任。
- **放行口径**：覆盖短断线后重连、超过宽限、服务端重启、节点丢失进度及取消／超时。可恢复时只在原节点恢复，重复下发不重执行，上报补发不重复落库；不可恢复则说明受阻原因、释放设备和租约，不改判通过。`need_human` 的安全停住与事后审核分开，不能用审核页代替执行中接管。P2 收口时用这些故障场景评估数据库状态机是否够用，记录是否需要引入 Temporal，本稿不预设结论。

### P3：先验脚本回归，再放行自愈

- **已有证据（历史记录）**：Python／pytest 运行时和 Rust 生成核心、静态校验、开发入口已有记录。生成验收用了假 Claude，产物到内存或标准输出为止；静态校验通过不等于真机自检通过。任务 C 的 3 个本地监听相关检查被沙箱拦住，也不能算通过。
- **先验回归**：只从 Judge 整体通过且每条预期有唯一通过项的历史执行生成候选。候选不合规拒绝入库，合规后先收集、再在同一受控测试环境自检，通过才按用例版本归档，记录来源执行、脚本版本和内容摘要。至少一个获准脚本能从平台入口选版本回归，正常路径零模型调用；用受控的预期不匹配场景证明断言会失败，超时／取消可收尾并释放资源。静态校验不是沙箱；脚本模式也须验账号、设备及执行边界，失败证据按可见范围脱敏，原始截图不当成已脱敏产物。
- **再验自愈**：用「定位失效」与「业务行为错误」各一例验分流。前者只产出可追溯的候选版本，重新自检通过并复核后才启用，可回退；后者保留失败并进入缺陷流程。分不清就交人工，额度耗尽或自检失败保留原结果和版本；不得改弱断言或把原失败改记为通过。

### 后续里程碑（建议，未立项）

- **P4：Web／接口与需求驱动测试。** 先确认试点 PRD、接口文档版本和隔离测试数据。用一个 Web 用例、一个有正反断言的业务接口用例，验证需求条目到用例、运行、证据和人工处置可追溯；再用一次文档版本变更证明能列出、复核并只执行受影响的用例、将关联脚本标为待更新，未影响项不误触发，测试数据可恢复。
- **P5：iOS 与扩面。** 先在一台已授权 iOS 测试机验证同样的派发、判定、证据和清理链路，执行时不依赖 Xcode；再验收一个批准来源的新包只触发一次指定回归，版本与结果可追查，设备矩阵区分通过、失败、未覆盖。多角色实例、弹窗规则库、崩溃日志、通知、项目经验库、UI 还原度和抓包对比按试点需要另立验收项，不计入已交付。
- **P6：治理与分享。** 保持当前无登录页的约束；扩大人员范围、引入身份或分享前另行确认。获准后用不同身份验证最小权限、越权拒绝、操作可归责和分享可撤回；证据留存与删除可核验，Agent 考核以可追溯的判定与人工复核数据为准。即使有更早的分享需求，这些门槛也不能后补。

## 三、验收记录要求

每期先做验收再正式进入下一期。验收表记录日期、版本、场景、预期与实际、执行编号或证据及未通过原因；区分替身／静态检查、数据库集成和已授权真机结果，不能互相替代。无证据标「未验证」，环境受限标「阻塞」。本稿只对照文档，不发起或重跑测试，不连接设备，不调用模型。
